## 1. F-009 问题与设计

### 1.1 5001拍的来源（62a4d38，调度器V1.11）
宏帧末拍（`macro_tick_o == MACRO_LAST_TICK`，即4999）时，主FSM的帧末处理清`B_FRAME_ACTIVE`、frame_id加1、tick回0。下一拍`flag_frame_start_eligible`要求`!state_current[B_FRAME_ACTIVE]`才成立，再下一拍新帧tick 0开始，因此相邻宏帧起点相差5001拍。唯一的例外是CAL→CAL校准滚动（`flag_calibration_rollover`，F-010后带生命周期门控），它本来就是5000拍。合同FSC-03（C08 §4.2）要求相邻宏帧起点严格相差5000拍。

### 1.2 修改（`ppg_400hz_frame_calibration_scheduler.v` V1.12）
- 新wire `flag_next_frame_inputs_eligible`：NORMAL/光学关闭宏帧的输入侧起帧资格，即
  `i_allow_new_transaction && (OPTICAL_OFF || (i_normal_measurement_eligible && !i_switch_hold_new_transaction))`。
  原`flag_frame_start_eligible`改用这根wire，逻辑等价。
- 新wire `flag_frame_restart`（`@satisfies: FSC-03`），成立条件：
  `B_FRAME_ACTIVE && macro_tick_o==MACRO_LAST_TICK && !flag_calibration_rollover && flag_lifecycle_active && i_active_config_valid && (state_next[B_CAL_REQ_PENDING] || flag_next_frame_inputs_eligible)`。
  门控与F-010滚动相同。只由覆盖层组合块读取，主组合块不读，因此无组合环。
- 覆盖层组合块（产生`state_rollover_next`）在滚动分支后增加`else if(flag_frame_restart)`，用与空拍起帧块相同的初始化建立新帧：
  - 模式：`state_next[B_CAL_REQ_PENDING]`成立则为CAL，否则为NORMAL；
  - 冻结光学模式、精度（CAL强制9位）、输入源、AMB/DC码与epoch、LEDDAC快照；
  - tick、sub、local归零；RED/IR是否需要按光学模式；DONE、FAILED、WAVE_PENDING清零；CONTEXT_SEEN放开；MACRO_START置1；
  - 有pending请求时：转为`REQ_ACTIVE`，类型、颜色、原因取`state_next`。
  - 取`state_next`是为了包含本拍握手和CAL帧末未提交请求的跨帧重挂。在途owner不重挂（L-1）由帧末处理保证，原样继承。
- 不改：在途owner（`B_INFLIGHT`及身份字段）、L-4过期候选门控、作废匹配释放、截止逻辑、F-010滚动门控、L-3空闲边界、空拍起帧路径。
- 适用全部帧末（统筹审核点A）：NORMAL→NORMAL、NORMAL→CAL、CAL→NORMAL、CAL→CAL重挂。CAL→CAL滚动仍走原路径，逐位不变。

### 1.5 起帧采样输入清单（统筹要求2）
起帧（无论重启还是空拍起帧）采样的输入及其更新时机：

| 输入 | 来源 | 更新时机 | 是否可能在4999后一拍才变 |
|---|---|---|---|
| i_active_config_valid / i_input_source / i_optical_mode | 配置管理器ACTIVE快照 | 只在COMMIT与STOPPING完成时变 | 否（RUN内静态；生命周期变化已由`flag_lifecycle_active`门控） |
| i_allow_new_transaction | 生命周期 | 只在生命周期跳变时变 | 否（同上） |
| i_leddac_r_code / i_leddac_ir_code | 常量C_LEDDAC_* | — | 否 |
| i_active_precision_mode | 精度窗口控制器 | 只在安全边界提交（`MACRO_SAFE_TICK`=4760） | 否 |
| i_switch_hold_new_transaction | 精度窗口控制器 | 随其状态机（进入/返回等待、重获取） | 否；不由帧末事件驱动 |
| i_normal_measurement_eligible | AMI组合：run_enable、config_valid、startup_search_complete、故障阻断 | 启动完成在IDAC提交边界（4760或校准local 385） | 否 |
| i_amb/dcs_*_code、*_epoch | IDAC码控制器 | 只在IDAC安全边界提交（4760、校准local 385、启动/空闲边界） | 否 |
| i_calibration_sample_valid（保持型请求） | AMI仲裁 | 重检或启动请求源成立且无在途请求时置位 | 见下 |

结论：帧末事件本身（`o_normal/calibration_frame_complete_event`、frame_id）都是寄存输出，在4999后一拍才可见。其消费者（如重检调度器对NORMAL帧完成计数后发起请求）最早在4999后第2拍更新输出。所以在4999采样（新）与在空拍采样（旧）看到的值相同，新帧类型序列不变。唯一会出现非5000间隔的情形是§4的残余项C（INFLIGHT挡住末拍握手）。实测：4份带监视器的系统TB在最终回归中非5000间隔数均为0（§8.3）。

## 6. L-6（工作会话中曾暂称N-2）：STOP落在波形接管与owner提交之间后立即START的静默卡死（既有缺陷）

### 6.1 发现与定性
F-009回归中`tb_ppg_control_top_adc_anomaly`为26/12。根因不是F-009：把旧调度器（62a4d38）的STOP移到tick 1同样卡死（探针f009_t1_old）。F-009只是让该TB的原STOP时刻（相对帧起点前移若干拍）落进了这个既有窗口。

### 6.2 机理
1. tick 0：RED波形上下文已交给SSW（`flag_red_context_valid=1`），owner要在tick 1之后才提交。
2. STOP确认落在tick 1。manager的`flag_stopping_complete`立即成立：ADC空闲，数据链排空，IDAC空闲，analog_safe也仍为1（RED包络tick 44才开始）。于是立即回到CONFIG。
3. TB随即COMMIT+START。调度器复位并进入STARTUP_PENDING，tick冻结在0。
4. SSW的上下文只在波形末拍或abort时释放。tick冻结后永远到不了末拍，因此`o_sar_timing_idle`恒为0，启动边界永不出现，新RUN永久静默停顿（无故障、无sticky）。

### 6.3 修改（`ppg_sar9_sar15_safe_selection_wrapper.v` V1.8，无新端口）
- 新wire `flag_start_restore = i_start_ack_event && !adc_owner_inflight_o && i_adc_idle`。它替换原来六处START恢复条件（`i_start_ack_event && o_wrapper_idle`）：
  - `reg_run_active`；
  - `calibration_timeout_sticky_o`、`owner_deadline_timeout_sticky_o`、`switch_protocol_error_sticky_o`、`transaction_mismatch_sticky_o`；
  - `flag_ssw_fault_identity_valid`。
- 该条件成立时，与abort分支一样清除`flag_red_context_valid` / `flag_ir_context_valid` / `flag_cal_context_valid`以及`flag_stop_pending`。
- 前提：STOPPING完成要求`i_adc_idle && i_datapath_empty && i_idac_idle && i_analog_safe`（manager `flag_stopping_complete`），所以START时不可能有已提交owner在途。新条件保留`!adc_owner_inflight_o && i_adc_idle`两项防护：万一前提不成立，行为退回旧版（不恢复），不会丢弃在途owner。
- 相关波形寄存器核查：各色波形快照寄存器（精度、run generation、帧身份等）只在对应`flag_*_context_valid`为1时被读取。上下文作废后它们不再被使用，下一次接管会整体覆盖，因此无需清除。owner侧寄存器（`adc_owner_inflight_o`及身份）不受影响。
- 无合同编号，按L-6记录；未打@satisfies。合同补充交B（§9）。

## 7. long_10：GROUP5_NO_STALE_CONTEXT 判据精确化（服务F-009）

### 7.1 现象
F-009回归中long_10为128/1：结果8000，事务8002，原判据只容忍差1。

### 7.2 探针结论
缩小规模（40帧/100 ms，与4000帧/10 s的帧对齐相同），新旧调度器结果一致。差额由两部分组成：
- (a) START前残留1笔：JNT-09前缀中一次Q3释放被`flag_jnt_manual_adc_hold`挡住。hold撤销后，bg_responder在CONFIG中、本组START前约5 µs把它计成1笔RED。全规模旧基线所谓"少1笔"就是这一笔，并不是V1.3注释所说的STOP边界丢弃。
- (b) STOP边界合法丢弃1笔（F-009后新出现）：相邻宏帧严格5000拍后，10 s到点时第4000帧已开始。STOP确认（tick 200）落在其RED owner提交之后。该owner按合同第13节迟到DONE规则1以success=0旁带释放（STOP原因），不产生正式结果，也不产生result_discard事件。旧调度器每帧多1拍，全规模累计约4000拍（2 ms），10 s时第4000帧尚未开始，所以没有这一笔。

### 7.3 修改（`tb_ppg_control_top_long_10_cycles.v` V1.4）
- 判据：正式结果数 + STOP原因丢弃数 == 本组START之后的RED+IR事务数，不再容忍差额。标签仍为TB本地的`GROUP5_NO_STALE_CONTEXT`。
- 新增TB本地计数：
  - `cnt_l10_base_responses`：START被接受时已计入的RED+IR数；
  - `cnt_l10_stop_completion_discards`：本组STOP确认后、AMI STOP排空期间（`flag_stop_result_draining`）且无abort或系统故障的success=0完成；
  - `cnt_l10_stop_result_discards`：本组STOP确认后、原因为STOP的正式结果丢弃。
- abort、系统故障、完成丢失类丢弃不计入；一旦出现，核算就不平。

### 8.3 帧间隔监视器
| TB | RUN起点数（F009_FRAME_FIRST） | 非5000间隔 |
|---|---|---|
| tb_ppg_control_top（smoke） | 17 | 0（旧RTL快测22个5001） |

adc_anomaly的两处非5000间隔都属于故意制造异常的场景，即例外C（§4）：
- SYS-CAL-LATE6SF：CAL→CAL，间隔5004（4空拍）。TB把校准DONE故意拖到子帧7 local 600，CAL帧末owner仍在途。L-1不重挂，滚动与末拍握手被INFLIGHT挡住，NORMAL资格不成立，要等owner释放后握手才起下一CAL帧。
- SYS-CAL-LOST：CAL→CAL，间隔5131（131空拍）。校准完成丢失，帧末owner在途，下一帧要等T-lost作废（SYSMON LOST age=4502）释放owner后才起帧。
- 旧调度器下同两处的实测见§8.4。

据此订正§4与附录A第9'行："间隔2个空拍"只是owner在末拍后立即释放时的最小值；一般情形下，空拍数由在途owner的释放时刻决定（正常迟到完成或T-lost作废）。

### 8.4 旧调度器对照（例外C为既有行为）
用同一套源码，只把调度器换回62a4d38版（V1.11），跑adc_anomaly（`phase2/runs/anom_oldsched`）。结果为ADC_ANOMALY_TB_PASS checks=40。这也说明换回旧调度器后，原STOP时刻碰不到L-6窗口，与§6.1"F-009只是让原STOP时刻落进既有窗口"一致。

| 间隔类型 | 旧调度器 | 新调度器 |
|---|---|---|
| NORMAL→NORMAL 5001 | 649 | 0 |
| NORMAL→CAL 5001 | 2 | 0 |
| CAL→NORMAL 5001 | 3 | 0 |
| CAL→CAL 5004（SYS-CAL-LATE6SF） | 1 | 1 |
| CAL→CAL 5131（SYS-CAL-LOST） | 1 | 1 |

结论：例外C的两处间隔在新旧调度器下完全相同，是既有行为，不是F-009引入的；F-009消除了其余全部非5000间隔。
