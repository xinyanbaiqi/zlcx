## 0. 为什么还需要这份计划

用户问过："多轮仿真都过了，为什么RTL/TB还有错？"回答是：回归只证明"没有变坏"，不证明"是对的"。几轮下来查出的缺陷，集中在以下几类：

| 类别 | 实例 |
|---|---|
| 同拍冲突，TB从未构造 | tick-248截止与提交同拍；F-010滚动覆盖abort；F-023；L-4 |
| ADC异常与生命周期异常，TB从未覆盖 | L-1错绑（基线回归中静默存在了很久）；L-3/L-4卡死；冗余校正器作废死锁；L-6 STOP后立即START静默卡死 |
| TB跑到了场景，却没检查相应字段 | F-019；P2S错拍；F-011放过5001 |
| TB与RTL同源错误 | F-005（两边都按下降沿理解） |
| 编号与覆盖不对应 | FSC全族同号不同义；PASS计数与合同覆盖对不上 |
| 容差掩盖错误 | long_10的"允许差1"掩盖了TB计数口径错误 |
| 修复引入新问题 | tick-248；生命周期轮第二步漏掉的冗余校正器死锁 |
| 合同没写到的需求 | L-2（ADC失联的处理） |

本计划用不同性质的手段，分别补这些盲区：
- 系统排查同拍冲突；
- 逐拍扫描加活性监视；
- 覆盖率；
- 变异测试；
- 只按合同写的独立模型；
- 关键协议性质的断言验证（不装形式工具，见V7）；
- SSW 32路控制输出的逐拍黄金比对（V18）；
- 逐ID动态闭环；
- 外部独立审查。

每项都写明：范围、方法、执行者、开始时机、通过标准、证据形式。

### V1 同拍冲突矩阵
- **目的**：系统地找出"多个置位、清零、装载条件同拍到达"时，RTL优先级与合同不一致的地方。这是本项目缺陷最集中的一类。
- **范围**：控制面全部有两个以上置位、清零、装载条件的寄存器和计数器，涉及调度器、AMI、SSW、supervisor、重检调度器、PWI/PWC、IDAC控制器、manager、冗余校正器、SPI诊断路径。生命周期轮预审已做过AMI、调度器、SSW的新增部分，可复用。
- **方法**：逐个寄存器列出全部条件和RTL优先级，枚举可能同拍到达的事件对。每对给出处置：
  - (a) 构造上互斥，写出理由；
  - (b) 优先级与合同一致；
  - (c) 不一致，记为发现。
  能用扫描或断言验证的标注出来，交V2、V7。
- **执行**：新会话或子代理，只读。统筹核实(c)类。
- **时机**：P0即可开始（B期间RTL冻结）。
- **通过标准（建议）**：100%事件对有处置；(c)类全部在P3修复，或经用户裁定写进合同。
- **证据**：`verification_reports/`下的冲突矩阵表，每对附RTL符号与合同节号。
- **状态（10-09，已完成）**：
  - 12个控制模块各做了两遍互相独立的审查：云端在分支`p0-closure`（`d25b943`，`verification_reports/p0_closure/`），另一个AI在分支`v1-independent`（`8dee3cd`，`verification_reports/v1_independent/`），基线都是`a1ba482`。
  - (c)类发现：云端24项，另一个AI 18项，重叠度高。各有对方漏掉的真实问题：AMI-C1只有云端发现，V1-AMI-03只有另一个AI发现。
  - 统筹逐条核实后，用户裁定：9项RTL修复（含高严重度的SSW-C1：双光SAR9下RED三个使能被IR段覆盖），13项只写合同，其余待验证组合并入V2/V7。清单见修复与补测试轮任务书。

### V2 逐拍时序扫描与故障注入（含活性与身份监视）
- **目的**：不只测几个点，而是把异常事件放到一帧中的每一拍去试。L-6就是这样才被发现的。
- **注入事件**：STOP、abort、START延迟、ADC DONE丢失、DONE迟到、ADC卡忙后恢复或永不恢复、精度切换请求、诊断清除、配置COMMIT。
- **工作模式**：NORMAL双光与单光、启动搜索、周期重检；SAR9与SAR15。
- **扫描网格（建议）**：
  - 关键窗口逐拍扫：tick 0~2、160~162、248~250、266、283~285、309~311、385、443~445、477~479、4499~4503、4760、4808~4812、4999~5001，以及各子帧的local 0~2、248~250、385；
  - 其余位置步长不大于25拍。
- **常驻监视器**（建议做成可复用的TB模块）：
  1. 活性：RUN或STOPPING中连续3帧既无进展也无故障记录，判FAIL；
  2. 身份记分板：每个正式结果与其owner的帧号、序号、颜色一致，排除合同前提允许的约2拍窗口；
  3. 恢复检查：STOP、诊断清除、COMMIT、START之后，必须重新出帧；
  4. 帧间隔监视：沿用F-009的监视器，非5000间隔只允许出现在已登记的例外中。
- **必须覆盖的已知项**：
  - F-1：用真实检测链触发精度切换，再叠加IR丢失；
  - 校准owner纯丢DONE跨入NORMAL帧的变体（用户10-09裁定放在这里）；
  - L-6扫描扩展到RED、IR、CAL完整窗口；
  - 例外C；
  - SID-05截止跨帧重试；
  - 迟到完成跨帧；
  - SAR15下的作废时序；
  - cause 07在芯片层的可观测性（生命周期报告§7.1(e)）；
  - 冗余校正器作废前1~2拍DONE进入同步链的逐拍验证；
  - 两份V1报告中标"待定"或"建议扫描"的条件对（逐条列入扫描矩阵，结论回填V1）；
  - ADC转换时延按2~20拍覆盖，两端再外扩（见V15）。
- **执行**：一个专门会话。新TB文件P0可先写，正式运行和登记进回归放在RC1之后。
- **通过标准（建议）**：
  - 全部扫描点要么按合同恢复，要么与已登记的例外行为完全一致（F-1、例外C、F-2等）；
  - 0次静默停滞；
  - 合同前提窗口之外0次错绑。
- **证据**：扫描矩阵结果表，含每个点的结论和日志位置；新增TB入回归。

### V4 覆盖率
- **目的**：量出从未执行过的RTL分支、状态和转移。
- **方法**：用Vivado 2022.2 xsim的代码覆盖率功能（xelab的覆盖率选项加`xcrg`出报告），**先在一个TB上试跑，确认工具支持与开销**。在全套回归上汇总语句、分支、条件、FSM状态与转移，以及顶层端口翻转。
- **执行**：P0试跑；正式统计在RC1上做。
- **通过标准（建议）**：
  - 控制面模块：语句100%，或逐条说明不可达原因；分支和条件不低于95%，余下逐条说明；可达FSM状态与转移100%；
  - 数值通路模块：语句和分支不低于95%；
  - 顶层端口翻转100%，常量端口除外。
  - 每个未覆盖点要么补测试，要么写不可达理由并经统筹核实。
- **证据**：覆盖率报告，以及未覆盖点的处置表。

### V5 变异测试
- **目的**：检验TB是否真能抓到错误。以往各轮都做了针对性负对照，这里改为系统化。
- **方法**：对控制面RTL自动注入变异，每次只改一处，跑相关TB子集，统计被杀死的比例。变异类型包括：条件取反、去掉一个与项、交换if/else if优先级、计数器边界±1、复位值翻转、门控去掉一项。存活的变异逐个分析：等价变异，还是缺检查需补测试。
- **执行**：RC1之后，可脚本化。耗时较长，需要分组并行。
- **通过标准（建议）**：控制面杀死率不低于90%；每个存活变异都有处置（证明等价，或已补测试）。
- **证据**：变异清单、结果表、存活项处置。

### V6 独立参考模型与独立TB
- **目的**：防止TB与RTL犯同一个错误（F-005就是这样）。
- **方法**：由一个**没看过RTL**的会话，只按合同编写事务级或周期级参考模型，与RTL的仿真轨迹逐事务比对。优先：
  1. SPI读写地图与各位的清除语义；
  2. owner生命周期（提交、完成、作废、错配、STOP/START）；
  3. 帧时序与校准阶段推进；
  4. ADC数值通路（已有Python黄金模型的部分可复用）。
- **时机**：必须在B改完合同之后写，否则模型依据的是旧合同。
- **通过标准（建议）**：比对0个未解释差异；每个差异落实为RTL缺陷、合同缺陷或模型错误。
- **证据**：模型代码、比对报告。

### V7 断言验证（关键协议性质；用户10-09决定不装形式工具）
- **目的**：把关键协议性质写成断言，在所有仿真场景中持续检查。
- **方法**：
  - 性质写成断言检查模块（xsim支持SVA并发断言；也可以写成Verilog监视逻辑），放在单独文件，不改RTL；
  - 挂进全部系统TB、V2的扫描和长时间随机运行。
- **局限（如实记录，写进最终签核材料）**：这只能证明"跑到的场景里没有违反"，不是证明。"不会死锁""L-5不可达"这类结论，只能靠V2扫描的覆盖面加上V1、V11的分析来支撑。
- **建议首批性质**：
  1. owner唯一：任一时刻至多一个ADC事务在途，且与调度器、SSW、AMI三方记录一致；
  2. 作废与完成互斥：同一owner不会同拍既作废又完成；
  3. 冗余校正器不变量：`(capture_pending ∨ capture_valid) ⇒ (context_valid ∨ drop_armed)`；
  4. START后可恢复：L-6修复后，START确认时没有残留的波形上下文；
  5. L-5"生产构建下系统级不可达"的证明（用户10-09裁定放在这里）；
  6. 各故障lane在规定事件后一定落下；
  7. 有界活性：RUN中，在规定拍数内必有进展或故障记录；
  8. IDAC控制器处于IDLE时，没有挂起的valid（修复轮任务书中的附加要求）；
  9. 两份V1报告中建议做成断言的条件对。
- **执行**：P0写断言；正式运行在RC1上，和V2一起跑。
- **通过标准（建议）**：全套回归、V2扫描、长时间随机运行中，所有断言0次违反；每个断言都要有负对照，证明它能报错。
- **证据**：断言文件、运行日志、负对照记录。

### V15 模数接口行为校准（补充）
- **目的**：所有TB里的ADC、IDAC、模拟时序都是数字侧编写的行为模型。如果行为模型与真实模拟电路不符（DONE脉冲宽度与时刻、`analog_safe`时序、异步捕获时序、IDAC建立），仿真全部通过，芯片仍然可能出错。
- **方法**（据V12答复简化：没有AMS模型，模拟侧抽象为9位和15位两个SAR ADC）：
  - 逐个核对各TB中的ADC行为模型是否符合用户确认的四条：
    1. CLK_STAGEx_DOUT上升沿表示转换结束，电平保持到下一次转换开始的下降沿；
    2. 转换完成后DOUT稳定；
    3. ADC空闲后不会出现旧DONE；
    4. Q3到DONE上升沿约1~10 µs（2~20拍）。
  - 不符的TB模型列出差异，判断差异是"更保守"（可保留）还是"会掩盖问题"（要修改）。
  - V2扫描中的转换时延按2~20拍覆盖，另加两端外扩，作为容差余量。
  - "DONE丢失"只作为故障注入场景使用（用户确认几乎不会发生）。
- **时机**：P0，可由云端只读完成。
- **通过标准（建议）**：所有TB的ADC模型都符合上述四条，或差异经判定为保守。

### V16 第二仿真器交叉检查（补充）
- **目的**：只用xsim一种仿真器，可能掩盖依赖仿真器事件调度顺序的竞争写法：仿真里能过，综合后的硬件行为却不同。
- **方法**：用iverilog（Verilog-2001可编译）跑关键TB子集，比对PASS行与`$finish`。差异逐个分析，确认是RTL竞争、TB竞争还是仿真器差异。可以在云端做，云端没有Vivado但可以装iverilog。
- **时机**：RC1之后。
- **通过标准（建议）**：关键TB在两种仿真器上结果一致，或差异全部有解释，且确认不是RTL竞争。

### V17 主机软件编程与恢复指南（补充）
- **目的**：很多正确性依赖主机软件按规定流程操作，例如F-1、F-2之后的"诊断清除→COMMIT→START"、lost sticky的读取与清除、STOP的使用。芯片按合同工作，软件流程用错，整机照样会出错。
- **方法**：从B之后的合同整理一份面向软件的编程指南，内容包括：寄存器地图、各位的清除语义、启动、停止、故障恢复流程、已知例外，交软件团队。用V6的独立模型或芯片TB，把指南中的每个流程实际跑一遍。
- **必须写明**：`0x0114`/`0x011B`作废锁存的翻转位只能反映奇偶，主机须在每次STOP或abort之后、下一次START之前读取这两个寄存器（X-009，见V11）。
- **时机**：B合并之后。
- **通过标准（建议）**：指南中的每个流程都在TB中验证过。

### V18 SSW 32路模拟控制输出逐拍黄金比对（10-09新增，高优先级）
- **起因**：云端V1发现SSW-C1：双光SAR9时，红光窗口内`EN_9_IREF/AMB/DC`被IR段覆盖为0，用户确认这3个使能必须为1。这个缺陷一直没被发现，因为没有任何TB检查SSW的控制输出引脚，ADC行为模型也不看这些引脚。用户确认过"SSW符合合同即符合模拟需求"，所以SSW输出的逐拍正确性是芯片功能正确的直接依据。
- **方法**：按C09合同中的时序表，编写独立的逐拍期望波形发生器（只依据合同，不看SSW RTL）。在以下全部组合下，与SSW的32路输出（`o_clk_*`、`o_en_*`、`o_idac_*`等）逐拍比对：
  - 单光RED、单光IR、双光；
  - SAR9、SAR15；
  - NORMAL、AMB校准、DCS校准；
  - 精度切换前后的帧；
  - STOP/abort落在波形中途。
  可以先做SSW单元级，再在芯片顶层引脚处复核一次。
- **时机**：RC1前的修复轮先给双光SAR9的这3个使能加检查和负对照；完整比对放在P2，排在V2之后的第二优先。
- **通过标准（建议）**：全部组合下32路输出与合同时序表逐拍一致，0个未解释差异。

## 4b. 本计划无法消除的剩余风险（如实列出，签核时由用户接受）

- **没有形式证明**：死锁和不可达类结论只能靠扫描覆盖面加分析来支撑。超出扫描网格的情况，以及两个以上异常叠加的情况，可能遗漏。

- **模拟侧真实行为**：没有AMS或SPICE模型（V12第10条），V15只能核对TB行为模型是否符合用户确认的四条事实，不做联合仿真，无法覆盖PVT全空间。
- **实现层问题**：综合与仿真不一致、时序、亚稳态、DFT等，要靠V14后端签核解决，RTL仿真覆盖不到。
